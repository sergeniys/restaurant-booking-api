# Restaurant Booking API

REST API для онлайн-бронирования столиков в ресторане.  
Выполнено в соответствии с ТЗ со всеми бонусными требованиями.

---

## Стек технологий

- **Язык**: Python 3.11+ (протестировано на 3.11–3.14)
- **Фреймворк**: FastAPI
- **Схемы и валидация**: Pydantic v2
- **ORM / База данных**: SQLAlchemy 2.0 (asyncio) + SQLite (`aiosqlite`)
- **Миграции**: Alembic (async)
- **ASGI-сервер**: Uvicorn
- **Тестирование**: pytest, pytest-asyncio, httpx (`AsyncClient`)
- **Линтинг и типы**: Ruff, Mypy (`strict = true`)
- **Контейнеризация**: Docker, Docker Compose

---

## Быстрый запуск

### Вариант 1: Запуск через Docker Compose (одной командой)

```bash
docker compose up --build
```

Сервис запустится на порту `8000`. При запуске контейнера автоматически применятся миграции Alembic.  
Swagger-документация доступна по адресу: [http://localhost:8000/docs](http://localhost:8000/docs).

### Вариант 2: Локальный запуск

1. **Клонируйте репозиторий и перейдите в каталог**:
   ```bash
   git clone https://github.com/sergeniys/restaurant-booking-api.git
   cd restaurant-booking-api
   ```

2. **Создайте и активируйте виртуальное окружение**:
   ```bash
   # Linux / macOS
   python3 -m venv .venv
   source .venv/bin/activate

   # Windows (PowerShell)
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   ```

3. **Установите зависимости**:
   ```bash
   # Для продакшена
   pip install -r requirements.txt

   # Либо включая зависимости для тестов и разработки
   pip install -r requirements-dev.txt
   ```

4. **Примените миграции Alembic**:
   ```bash
   alembic upgrade head
   ```

5. **Запустите сервер**:
   ```bash
   uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
   ```
   Либо:
   ```bash
   python main.py
   ```

API готово к приёму запросов на [http://localhost:8000](http://localhost:8000).

## API Эндпоинты

| Метод | Путь | Описание | Коды ответов |
|---|---|---|---|
| `POST` | `/bookings` | Создать бронь (валидация, проверка слота, max 10 столов) | `201`, `422`, `409` |
| `GET` | `/bookings` | Список броней с сортировкой, фильтром по дате и пагинацией (`?date=...&limit=20&offset=0`) | `200`, `422` |
| `GET` | `/bookings/{id}` | Получить бронь по ID | `200`, `404`, `422` |
| `DELETE` | `/bookings/{id}` | Отменить бронь (мягкая отмена: `status="cancelled"`, освобождает слот) | `200`, `404`, `409`, `422` |

- **Интерактивная документация Swagger UI**: `/docs`
- **Документация ReDoc**: `/redoc`

## Принятые решения и их обоснование

1. **Разделение схем `BookingCreate` и `BookingOut`**: Схема создания валидирует дату в будущем (до 90 дней) и время (слоты 12:00–22:00, не прошедшие сегодня по Москве), тогда как `BookingOut` наследуется от базовой схемы напрямую. Благодаря этому ранее созданные исторические брони при чтении из базы никогда не падают с ошибками валидации дат.
2. **Гранулярный `SlotLockManager` вместо глобальной блокировки**: Блокировка берется исключительно на кортеж `(booking_date, booking_time)`. Параллельные запросы на разные слоты выполняются независимо, а конкурентные запросы на один слот сериализуются в event loop одного процесса.
3. **Оптимизация SQLite через PRAGMA (WAL + busy_timeout)**: Включён режим WAL (`Write-Ahead Logging`) и `busy_timeout=5000`, чтобы параллельные чтения и записи транзакций не приводили к ошибке `database is locked`.
4. **Строгая валидация и часовой пояс `Europe/Moscow`**: Все временные расчеты жестко привязаны к часовому поясу Москвы через `zoneinfo.ZoneInfo`, отсекая расхождения на серверах в других часовых поясах. Строгий тип `StrictInt` исключает неявное приведение булевых значений (`True` -> `1`) и дробных чисел в поле `guests`.

## Реализованные бонусные баллы

1. **Async SQLAlchemy 2.0 + миграции Alembic**:
   - Использован полностью асинхронный драйвер `sqlite+aiosqlite`.
   - Настроен асинхронный Alembic (`alembic/env.py`) и создана миграция с индексами (включая составной индекс `ix_bookings_slot_status` по `(booking_date, booking_time, status)` для оптимизации проверки свободных столов).
2. **Пагинация списка броней**:
   - Параметры `limit` (от 1 до 100, по умолчанию 20) и `offset` (смещение >= 0).
   - В ответе возвращается `total` — суммарное число броней с учётом активного фильтра по дате.
3. **Защита от состояния гонки (Race Condition)**:
   - **Решение**: Реализован менеджер поэлементных блокировок `SlotLockManager` в сервисе. Блокировка берется исключительно на кортеж `(booking_date, booking_time)`. Запросы на разные слоты выполняются параллельно и независимо, а конкурентные запросы на один и тот же слот сериализуются.
   - База данных SQLite сконфигурирована в режиме `WAL` (`PRAGMA journal_mode=WAL`) с `PRAGMA busy_timeout=5000` для безопасной работы конкурентных транзакций.
   - Покрыто тестом `test_race_condition_protection`, в котором 10 параллельных запросов (`asyncio.gather`) с независимыми сессиями БД борются за 1 оставшееся место: ровно 1 запрос завершается успехом (`201`), а остальные 9 получают `409 Slot is fully booked`.
4. **Тесты на pytest + httpx.AsyncClient**:
   - Покрыты все позитивные и негативные сценарии: граничные даты (сегодня, 90 дней, 91 день), все форматы имен и номеров телефонов, запрет прошедших слотов, отмена и повторная отмена, ограничение в 10 столов, пагинация, сортировка и откат/накат миграций.
5. **Dockerfile и docker-compose**:
   - Настроен легковесный образ на базе `python:3.12-slim` с автоматическим накатыванием миграций при старте контейнера и монтированием тома для персистентности SQLite.
6. **Линтер и проверка типов (Ruff, Mypy)**:
   - Конфигурация в `pyproject.toml`.
   - Строгий режим `strict = true` в Mypy, форматирование по стандартам PEP 8 через Ruff.

## Что бы я доделал при наличии большего времени

1. **Масштабирование на несколько процессов/инстансов (Redis / PostgreSQL)**: Текущий `SlotLockManager` защищает от гонки в рамках одного асинхронного процесса. Для горизонтального масштабирования (несколько Uvicorn-воркеров или подов) локальный лок заменяется на распределенный лок в Redis (Redlock) либо транзакции PostgreSQL с уровнем `SERIALIZABLE` / явный `SELECT ... FOR UPDATE`.
2. **Rate Limiting**: Ограничение частоты запросов (slowapi / redis) на создание броней для защиты от спама и перегрузки.
3. **Очереди и уведомления**: Фоновые задачи (Celery / ARQ) для отправки Telegram/SMS подтверждений и напоминаний гостям за 2 часа до начала слота.
4. **Observability**: Метрики Prometheus и трейсинг OpenTelemetry для мониторинга времени выполнения запросов и загруженности ресторана.
